# Space Invaders Arcade (Python)

A retro-inspired Space Invaders style arcade game built with Python + Pygame.
This app is mostly generated by <ins>vibe coding</ins>.

## Quick Start

From the project root in PowerShell:

```powershell
.\setup_venv.ps1
.\run_game.ps1
```

That will create/activate `.venv`, install dependencies, and run the game.

## Gameplay Features

- **Intro Screen**: Press SPACE to start, with key bindings displayed
- **Sound Toggle**: Press M at any time to toggle background music and sound effects on/off
- Left/right player movement and shooting
- Classic alien formation movement with descending rows
- Speed-up as fewer invaders remain
- Destructible bunkers
- Mystery ship bonus target
- Multiple waves, score, lives, and game-over restart
- Retro synthesized sound effects (generated in code, no external audio files)
- Pixel-art sprite-sheet rendering for player, alien rows, bullets, and UFO
- Procedural arcade-style background music loop

## Controls

The intro screen displays all controls on startup. Here's a quick reference:

- `Space`: Start game (from intro screen) / Shoot (during gameplay)
- `A` / `Left Arrow`: Move left

#### Common Issues

- `ModuleNotFoundError: No module named 'invaders'`:
  Run tests from the project root, not from inside `tests/`.
- Pygame display/audio issues in headless environments:
  Use CI defaults or run in a normal desktop session; this test suite already includes basic guards for non-interactive runs.
- Wrong Python interpreter:
  Confirm with `python --version` and prefer `.\.venv\Scripts\python.exe` when in doubt.

## Modular Project Structure

- `main.py`: thin entrypoint that starts the game
- `invaders/config.py`: gameplay constants and color palette
- `invaders/geometry.py`: framework-agnostic rectangle model used by core state
- `invaders/models.py`: dataclasses for bullets, aliens, explosions, mystery ship
- `invaders/state.py`: single mutable game state container
- `invaders/factories.py`: state/object creation for aliens, bunkers, and starfield
- `invaders/ports.py`: protocol interfaces for input/audio dependencies
- `invaders/services.py`: update services for player control, world simulation, and wave transitions
- `invaders/audio.py`: procedural retro sound generation and playback
- `invaders/systems.py`: gameplay systems (movement, firing, collisions, lose checks)
- `invaders/renderer.py`: all drawing and HUD rendering
- `invaders/game.py`: orchestration loop, input handling, reset/wave flow

## Architecture Boundaries

### Dependency Direction

Dependency direction used by the project:

```text
runtime/orchestration (game.py, main.py)
              ↑
         adapters (input.py, renderer.py, audio.py)
              ↑
         services (services.py)
              ↑
         domain (state, models, systems, geometry, config)
```

### Layer Responsibilities

**Domain Layer** (pure rules/data; no framework imports):

In this context **domain**  means the game's brain: the core game data and rules that decide what happens in the game, independent of `pygame`, rendering, keyboard handling, or audio playback.

- `config.py`: gameplay constants (speeds, screen size, colors).
- `geometry.py`: rectangle model and collision math.
- `models.py`: data classes for game entities (`Bullet`, `Alien`, `Explosion`, `MysteryShip`).
- `state.py`: mutable game state container with framework-agnostic data.
- `systems.py`: deterministic core gameplay rule functions (movement, collisions, scoring/loss checks).

Domain is fully testable and reusable; no `pygame`, rendering, input handling, or audio IO here.

**Service Layer** (orchestrates state transitions, remains framework-agnostic):

- `services.py`: `PlayerController`, `WorldUpdater`, `WaveManager`.
- Consumes semantic actions (not key codes).
- Calls domain systems and coordinates update order.
- Triggers side effects through ports/callbacks (e.g., wave transitions).

Services are composable and easy to test with stubs/mocks.

**Adapter Layer** (translation boundary to frameworks):

- `input.py`: `PygameActionInput` maps `pygame` keys to semantic actions (`"move_left"`, `"shoot"`, etc).
- `renderer.py`: draws domain state onto a `pygame` surface; converts domain `Rect` for rendering.
- `audio.py`: procedural sound generation and playback behind an audio port.

Adapters are the only place framework types should appear.

**Runtime/Orchestration Layer** (wiring, lifecycle, frame loop):

- `game.py`: owns `pygame` init, display, clock, and event loop.
- Instantiates adapters and services.
- Translates `pygame` events to adapter calls.
- Calls service methods to update state.
- Calls renderer to draw.

Runtime wires components together; it should not contain core gameplay rules.

### Data Flow Example

The diagram below shows how a single player input travels through all architectural layers during one frame:

```text
[Hardware]  →  [Runtime]  →  [Adapter]  →  [Service]  →  [Domain]  →  [Adapter]  →  [Display]
  Key press     game.py      input.py     services.py    systems.py   renderer.py    pygame surface
```

**Step-by-step walkthrough (shooting example):**

| # | Layer | What happens |
|---|-------|-------------|
| 1 | **Hardware** | Player presses `Space`. |
| 2 | **Runtime** (`game.py`) | The `pygame` event loop receives a `KEYDOWN` event and forwards the key to the input adapter. |
| 3 | **Adapter** (`input.py`) | `PygameActionInput.action_for_key(key)` maps the `pygame` key constant to the semantic action `"shoot"`. No domain code sees the raw key. |
| 4 | **Runtime** (`game.py`) | Calls `PlayerController.update(state, dt, controls, sound)`, passing the semantic controls object. |
| 5 | **Service** (`services.py`) | `PlayerController` queries `controls.pressed("shoot")`, then delegates to the domain: a new `Bullet` is appended to `state.bullets`. |
| 6 | **Domain** (`systems.py`) | On the next `WorldUpdater` tick, bullet-movement and collision rules advance the bullet position and detect hits—pure deterministic logic, zero framework imports. |
| 7 | **Adapter** (`renderer.py`) | `renderer.draw(state)` reads the updated domain state and renders all entities onto the `pygame` surface. |

> **Key invariant:** Domain and service layers never import `pygame`. All framework coupling is isolated to the adapter and runtime layers.

### Boundary Rules

Use these rules as a quick architecture checklist when adding or reviewing code.

✓ **Do this:**

- Keep core gameplay rule functions in `systems.py` and domain data in `state.py`/`models.py`.
- Keep services orchestration-focused: call domain functions, coordinate flow, trigger callbacks.
- Keep adapters translation-focused: convert framework input/output to domain-friendly values.
- Use semantic action names in services (`"move_left"`, `"shoot"`), never framework key codes.
- Depend on protocols/ports (`AudioPort`, input contracts), not concrete adapter classes.
- Write tests at the seam: mock/stub adapters when testing services and domain behavior.

✗ **Don't do this:**

- Import `pygame` in domain or service modules.
- Put collision, movement, wave, or scoring rules in `game.py`, `renderer.py`, or `input.py`.
- Return `pygame` types from domain/service APIs.
- Read keyboard constants directly inside services.
- Couple services to concrete sound/input implementations.
- Mutate game state while rendering.

### Quick Placement Guide

- If it is a **core gameplay rule function**, put it in `systems.py`.
- If it is **state transition orchestration**, put it in `services.py`.
- If it is **pygame event/key mapping**, put it in `input.py`.
- If it is **drawing/UI/HUD**, put it in `renderer.py`.
- If it is **frame loop, lifecycle, and wiring**, put it in `game.py`.

### PR Self-Check (30 seconds)

- No new `pygame` import appears outside adapter/runtime files.
- Services accept semantic actions and ports, not framework objects.
- Domain functions remain deterministic and framework-agnostic.
- Rendering code does not introduce gameplay state mutations.
