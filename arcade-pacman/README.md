# Pacman Arcade (Python)

A retro-inspired Pacman style arcade game built with Python + Pygame.
This app is mostly generated by <ins>vibe coding</ins>.

## Domain Context

This project belongs to the **arcade game domain**, specifically a Pacman-like maze chase game.
The domain logic focuses on real-time movement, collision outcomes, scoring, and level progression.

Core domain entities and concepts:

- **Player (Pacman):** navigates the maze, consumes pellets, and avoids ghosts.
- **Ghosts:** AI-driven enemies that move through the grid and can end the session on collision.
- **Maze/Grid:** tile-based world that defines legal paths, walls, tunnels, and object placement.
- **Pellets:** collectible items with different score values that drive win conditions.
- **Session State:** current level, score, selected difficulty/theme, and game-over/win transitions.

Key domain rules implemented by this project:

- Movement is constrained by maze topology (walls, corridors, tunnel wrapping).
- Pellet collection updates score and determines level completion.
- Player-ghost collisions trigger lose states according to gameplay rules.
- Completing all required pellets advances the campaign to the next level.
- Difficulty settings influence gameplay behavior (pace/challenge level).

## Gameplay Features

- Start menu flow before gameplay starts
- Difficulty selection in menu: Easy, Normal, Hard
- Theme selection in menu: Classic, Neon
- Pacman + ghost movement on tile grid with tunnel wrapping
- Multi-level campaign with automatic progression
- Multiple pellet types with different score values and visuals
- Persistent local high score stored in highscore.json
- Retro synthesized sound effects (no external audio assets required)
- Audio toggle during play with M (and S in menu)

#### Common Issues

- ModuleNotFoundError for pacman:
  Run tests from project root, not from inside tests/.
- pygame display/audio issues in headless environments:
  Prefer a normal desktop session for local smoke tests.
- Wrong Python interpreter:
  Confirm with python --version and prefer .\.venv\Scripts\python.exe when in doubt.

## Modular Project Structure

- `main.py`: thin entrypoint that starts the game
- `pacman/config.py`: gameplay constants, difficulty and pellet definitions
- `pacman/models.py`: typed gameplay model configs
- `pacman/state.py`: mutable runtime game state container
- `pacman/factories.py`: pellet distribution and ghost spawn factory functions
- `pacman/systems.py`: pure gameplay systems (movement, pellet consume, collision checks)
- `pacman/events.py`: world update event payloads
- `pacman/session_service.py`: level/session orchestration
- `pacman/player_service.py`: action-to-player-direction control logic
- `pacman/world_service.py`: world step orchestration and event emission
- `pacman/renderer.py`: all game and HUD rendering
- `pacman/input.py`: key-to-action adapter
- `pacman/audio.py`: procedural sound generation and playback
- `pacman/storage.py`: high score persistence
- `pacman/game.py`: runtime loop and component wiring

## Architecture Boundaries

### Dependency Direction

Dependency direction used by the project:

```text
runtime/orchestration (game.py, main.py)
              ^
        adapters (input.py, renderer.py, audio.py)
              ^
   services/events (session_service.py, player_service.py, world_service.py, events.py)
              ^
domain (state.py, systems.py, factories.py, models.py, config.py)
```

### Layer Responsibilities

Domain Layer (pure rules/data):

- `config.py`: gameplay constants and score definitions
- `models.py`: typed model definitions used by domain/services
- `state.py`: mutable game state data
- `factories.py`: deterministic setup/distribution helpers
- `systems.py`: deterministic gameplay rule functions

Service Layer (orchestrates state transitions):

- `session_service.py`: level loads, resets, and game start lifecycle
- `player_service.py`: converts semantic actions to player intent
- `world_service.py`: world update order and event emission
- `events.py`: event contract between world update and runtime side effects

Adapter Layer (framework integration boundary):

- `input.py`: maps pygame keys to semantic actions
- `renderer.py`: translates game state into pygame draw calls
- `audio.py`: maps sound keys to actual playback
- `storage.py`: file persistence for high score data

Runtime/Orchestration Layer:

- `game.py`: owns pygame init/display/clock, processes events, runs update/draw loop
- `main.py`: process entrypoint

### Data Flow Example

Each gameplay frame follows a predictable pipeline from input to rendering:

1. `game.py` reads `pygame` events and clock delta (`dt`).
2. `input.py` maps raw keys into semantic actions (move, start, restart, toggle audio).
3. `player_service.py` applies movement intent to `GameState`.
4. `world_service.py` advances the simulation by calling `systems.py` rules.
5. `world_service.py` returns `WorldEvents` that describe side effects only (play sound, save high score, load next level, reset positions).
6. `game.py` executes those side effects through adapters (`audio.py`, `storage.py`, and session-level operations).
7. `renderer.py` draws the final `GameState` for that frame.

This separation keeps gameplay rules deterministic and testable, while framework and IO concerns stay in the runtime/adapter layers.
